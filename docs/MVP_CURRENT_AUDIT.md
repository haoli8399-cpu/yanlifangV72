# 演立方 MVP 当前开发状态审计

> 审计日期：2026-07-15
> 审计范围：V6.6 PRD、历史版本与治理文件、Git、PC/H5、后端、数据库、小程序、测试、Docker/发布和 Agent 规范。
> 本报告描述真实代码状态，不把 PRD 勾选项或可见页面视为已实现证据。

## 1. 当前产品基线

- 当前有效产品规格是 V6.6，入口为 [`PRD.md`](PRD.md)，完整文件为 [`PRD_V6.6.md`](PRD_V6.6.md)。
- 演立方是独立平台，后仰喜剧是第一家普通 Tenant；演员分为供应商合作演员与独立演员，但底层应统一为平台演员身份 + Tenant 合作关系。
- 产品业务 Agent 的 MVP 仍是一个主 Agent + 确定性工具。
- 当前代码稳定 Tag 为 `v0.1.0-alpha`，实现基线仍主要是 V4.7。PRD V6.6 不等于代码 V6.6。

## 2. 当前代码状态

- 仓库已有 PC/H5、Fastify 后端和 uni-app 小程序，共扫描到 421 个受治理文件、248 个源码资产。
- PC/H5 有多个角色入口和大量页面原型，但绝大多数业务路由直接引用 `src/shared/mock/`；仅看到预留或注释掉的 `/v1` 请求。
- 后端注册 32 组 API。约 25 组包含数据库查询，8 组明显使用进程内 Mock；同一业务域存在真实表和 Mock API 并存。
- 当前任务分支包含上一轮工作空间治理和本次协作文档改动，尚未提交；没有获授权的 V6.6 业务代码修改。
- 未发现测试文件、测试运行器配置或测试脚本。

## 4. 当前已经具备的能力

- 需求、机会、方案、报价、合同、支付、履约、评价等对象的页面或 API 基础。
- 方案 H5、供应商工作台、运营后台、移动 Web 和小程序的交互原型。
- 旧版演员评价、演员信誉分、信誉等级和变动日志。
- 后端可以在 Redis 不可用时启动，本地 `/v1/health` 实测返回 200。
- 后端类型/构建、PC/H5 构建、小程序构建可执行。

这些能力只能说明“存在可复用资产”，不能说明 F01–F43 已形成真实数据闭环。

## 5. 当前主要缺口

- 缺 V6.6 `Tenant`、`TenantMember`、平台角色、项目成员和强制 Tenant 上下文。
- 演员仍以单一 `company_id` 表达归属，缺平台 Actor、合作关系、Tenant 私有上架与独立演员 Tenant。
- 缺 Brief/方案/报价/合同/执行的完整版本关系和端到端真实 API 接入。
- 评价只支持旧双向模型；缺项目/Tenant/演员分层归因、原始证据、复核申诉、信誉置信度与推荐记录。
- 缺 Tenant 隔离、报价金额、状态机和关键 API 的自动测试。
- 缺可靠 Preview/Production 手工发布路径和经验证回滚路径。

## 6. PRD 与代码的主要差异

| V6.6 要求 | 当前代码 | 判断 |
|:---|:---|:---|
| 平台运营方与 Tenant 分离 | `admin/agent/performer/client` 旧角色，平台与 Tenant 语义混合 | 需要重建权限上下文 |
| 所有业务对象明确 `tenant_id` | 核心旧表没有统一 `tenant_id` | 高风险基础缺口 |
| 演员平台身份 + 多 Tenant 关系 | `performers.company_id` 单公司关系 | 需要新关系模型与迁移 |
| F01–F10 真实需求/方案闭环 | 页面和部分 API 主要为 Mock | 尚未完成 |
| 规则版本化报价 | 有价格配置/报价基础，未形成 V6.6 可追溯规则闭环 | 需要改造 |
| 分层评价与基础信誉 | 有演员评分/信誉旧模型 | 可抽取，不能直接沿用 |
| 高级平台推荐 | 仅有示例评分/排序和 Mock | MVP 后续平台能力，不应提前冒充 |
| 主 Agent + 确定性工具 | 有 AI/工具原型，未形成 V6.6 工具契约 | 方向一致，实现不足 |

## 7. 当前最优先的三个开发事项

1. 建立 F01–F43 的 PRD—代码影响矩阵，明确复用、改造、重建、未开始和返工项，冻结首个纵向切片。
2. 修复 PC/H5 的 2 个类型错误并处理 Lint 基线策略，让最低检查成为真实门禁。
3. 串行实现 F43/F39 的 Tenant 和演员关系地基，再打通 F01–F10 需求 → Brief → 方案 → 客户版真实闭环。

## 8. 当前最大的五个风险

1. **Tenant 越权风险**：当前 Schema/API 没有统一 Tenant 强制过滤，继续扩展会把隔离缺陷复制到所有模块。
2. **伪完成风险**：大量页面和 API 使用 Mock，视觉完整度高于真实业务完成度。
3. **高风险规则无测试**：报价、金额、状态机、评价归因和权限没有自动化保护。
4. **发布不可复现**：Compose 使用缺失/错误的构建目录，API 3001/3002、`/health`/`/v1/health` 不一致，部署脚本只显式执行 `001_schema.sql`。
5. **历史资产漂移**：`project-center/`、小程序重复源码、`v0-*`/`td-*` 演示路由和当前事实源并存。

## 9. 是否适合并行开发

当前不适合并行核心业务。Tenant、认证、Schema、共享类型、报价和首个纵向闭环必须串行。文档、独立纯样式或文件边界完全分离的低风险任务，在接口契约确定后可由两个开发实例并行。

## 10. 建议采用的最小研发 Agent 数量

采用三个角色定义：研发总调度、开发执行、独立审查。默认一个开发 Agent；审查 Agent 在交付点独立介入。项目负责人只与总调度交互。
