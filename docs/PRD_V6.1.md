## 0. 文档定位

V6.1 不是 V6.0 愿景的缩写版，而是把尚未验证的产品判断转换为一个可在六周内完成的真实业务实验。

本版本只回答四个问题：

1. AI 能否准确理解企业商演需求并减少重复沟通；
2. AI 能否基于真实案例、资源和价格规则形成可发送方案；
3. 客户自助表达与销售代录两种模式，哪一种更适合真实业务；
4. 产品是否进入真实商演流程并推动客户产生明确下一步动作。

六周验证不是六周开发冲刺。优先使用现有 V4.7/V5.0 页面、人工后台、轻量脚本、临时数据表和 Wizard of Oz 完成验证。只有“不开发就无法获得关键证据”的能力才进入开发范围。

V6.0 中第七周以后的平台建设、多 Agent、完整履约和产品化能力，全部改为证据触发项，不是默认执行计划。

## 1. 产品决策摘要

### 1.1 当前产品定义

演立方 V6.1 是一个服务于企业商演业务的 AI 需求与方案协作 Agent：

- 客户可以直接描述、补充和确认需求；
- 销售可以导入微信、文字或既有资料，减少人工整理；
- Agent 基于真实案例、资源和规则生成方案草稿；
- 软件负责事实、版本、价格、权限、状态和审计；
- 人负责方案审核、价格与档期确认、对外承诺和成交责任。

六周内不把产品称为“成熟双端平台”。双端协作是优先验证的产品假设，不是已经成立的市场事实。

### 1.2 核心分工

```text
AI：理解、澄清、检索、推演、解释和建议
软件：事实、规则、状态、权限、计算、版本和审计
人：审核、关系、价格、档期、承诺和最终责任
```

### 1.3 产品不是

- 通用活动问卷或聊天机器人；
- PPT、文案和海报生成器；
- 完整 CRM、OA、财务或履约系统；
- 活动商城、演员交易平台或自动竞价系统；
- 无人值守的全自动销售；
- 重新开发一套大而全的 V6 软件；
- 为展示多 Agent、RAG 或复杂架构而建设的技术样板。

## 2. 六周验证假设

| 编号 | 待验证假设 | 最低有效证据 | 不能作为结论的证据 |
|:---|:---|:---|:---|
| H1 | AI 能准确理解真实商演需求 | 留出样本测试 + 真实 Brief 经业务人员和客户确认 | 演示案例、主观觉得“写得不错” |
| H2 | AI 能形成可发送方案 | 真实销售审核后发送给真实客户，且仅需有限修改 | 只在内部展示的方案 |
| H3 | 客户愿意直接与行业 Agent 交互 | 真实客户完成对话并确认 Brief，且无销售代填 | 客户口头说愿意使用 |
| H4 | 销售端确实节省时间 | 与原流程基线比较，需求整理和首版方案时间下降 | 使用者感觉“更快”但没有记录 |
| H5 | 产品推动真实业务前进 | 客户进入方案沟通、修改、报价、候选或内部审批等明确里程碑 | 点开链接、点赞或泛泛回复 |
| H6 | 非创始人能够使用 | 至少一名非创始人连续四周在真实机会中使用 | 只有创始人演示或代操作 |
| H7 | 真实资源和价格可信 | 资源、价格、档期状态均有来源、更新时间和人工责任人 | Agent 根据历史文本自行推断 |

### 2.1 证据等级

```text
续费与转介绍
> 持续付费
> 持续使用
> 首次付费或真实成交
> 明确商业里程碑
> 真实方案发送
> 确认 Brief
> 提供真实业务数据
> 参加试点
> 口头认可
> 个人想象
```

低等级证据不能推翻高等级证据。六周结束时仍未走完销售周期的机会，应继续观察 30—60 天，但不能把“尚未丢单”视为成功。

## 3. 验证对象与边界

### 3.1 第一真实业务场

后仰喜剧企业商演业务是第一验证场、数据来源和首批使用环境。验证必须使用真实历史样本和真实在谈机会，不能只使用为了测试而编写的理想需求。

### 3.2 初始场景选择规则

六周验证最多选择两个商演场景。Week 0 按以下规则确定：

1. 历史上存在不少于 10 个可用需求或方案样本；
2. 资源、报价和履约规则相对可确认；
3. 六周内较可能出现真实在谈机会；
4. 后仰销售和策划人员熟悉；
5. 方案价值不只是通用文案生成。

若只有一个场景满足条件，只验证一个场景。团建、年会、发布会、客户答谢等不得在没有样本的情况下同时纳入。

### 3.3 验证用户

| 用户 | 六周任务 | 产品责任 |
|:---|:---|:---|
| 客户需求发起人 | 描述需求、回答关键追问、确认 Brief、查看并反馈方案 | 只确认自身需求，不承担内部价格与资源责任 |
| 销售/商务 | 导入需求、补充事实、审核 Brief、推进客户 | 对客户关系、发送动作和商务信息负责 |
| 方案审核者 | 判断方案是否可发送、记录修改量 | 对方案专业性负责 |
| 资源与价格审核者 | 核对资源、档期状态、成本和报价 | 对确定性经营事实负责 |
| 最终承诺责任人 | 批准价格、档期和对外承诺 | 对外部承诺承担最终责任 |
| 验证记录者 | 记录时间、错误、修改和里程碑 | 不参与结果美化 |

六周内不建设复杂组织角色体系。一人可兼任多个内部角色，但审核责任必须在记录中明确。

## 4. 核心业务流程

### 4.1 路径 A：销售代客户导入

```text
销售收到微信/文字/现有文件
→ 导入真实需求
→ Agent 提取事实、推断和缺口
→ 销售核对来源并补充
→ 将 Brief 发给客户确认或由销售代确认
→ 进入方案生成
```

该路径验证“销售副驾驶”价值，也是客户不愿直接使用时的业务兜底。

### 4.2 路径 B：客户直接表达

```text
销售向真实客户发送专属邀请链接
→ 客户阅读 AI 身份和数据使用说明
→ 客户以文字描述需求
→ Agent 只追问影响方案、价格或履约的关键问题
→ 客户确认 Brief
→ 销售收到机会和已确认事实
```

客户直接表达必须与路径 A 分别记录完成率、耗时和 Brief 质量，不能混合统计。

### 4.3 方案生成与发布

```text
确认 Brief
→ 结构化条件筛选真实案例和资源
→ Agent 生成两套有实质取舍的方案
→ 确定性规则计算报价和毛利
→ 风险门禁检查价格、资源、档期与承诺
→ 人工审核和修改
→ 生成不含内部字段的客户版快照
→ 人工点击发送
```

“两套方案”必须在资源组合、活动结构、预算或体验取舍上不同，不能只是标题和措辞不同。

### 4.4 客户反馈与商业里程碑

```text
客户查看方案
→ 对方案方向或模块反馈
→ 销售记录反馈和下一步
→ Agent给出修订建议
→ 人工决定是否修改
→ 记录明确商业里程碑
```

六周内的商业里程碑包括：

- 正式方案已发送；
- 已完成方案沟通；
- 客户提出明确修改；
- 进入正式报价；
- 进入候选名单；
- 进入客户内部审批；
- 成交；
- 明确丢单并获得原因。

履约系统不属于六周核心范围。若六周内成交，只生成标准交接包，并通过现有流程完成履约。

## 5. 六周最小验证产品

### 5.1 必须具备

#### 输入与 Brief

- 销售粘贴真实文字需求；
- 客户通过专属链接进行文字对话；
- 原始输入保留来源、时间和提供者；
- 区分已确认事实、系统推断和待确认问题；
- 关键缺口动态追问；
- Brief 版本化并支持客户或销售确认；
- 对每个关键事实保留证据引用。

#### 案例、资源与方案

- 使用经人工审核的最小案例库；
- 使用经授权的公开资源信息；
- 先使用结构化条件过滤，再按需进行语义排序；
- 生成两套实质差异方案；
- 资源推荐显示来源、状态和最后更新时间；
- 待确认档期不得表述为已确认。

#### 价格、风险与审核

- 成本、报价和毛利由确定性规则计算；
- 规则具备版本号，计算过程可复现；
- 高风险规则先于 LLM 判断执行；
- 价格、档期、资源和承诺必须人工确认；
- 审核界面区分 Agent 生成内容与人工确认责任。

#### 发布、反馈与评估

- 复用现有客户方案 H5 或轻量页面；
- 发布不可变的客户版快照；
- 客户版不包含成本、毛利、底价、内部备注和其他客户信息；
- 记录客户查看、反馈和下一步商业动作；
- 记录模型版本、提示词版本、耗时、成本、人工修改和失败原因；
- AI 不可用时可以保存输入并转人工处理。

### 5.2 允许人工完成

以下工作可以由人工后台或 Wizard of Oz 完成，只要过程如实记录：

- 案例和资源入库；
- 资源公开信息脱敏；
- 价格规则配置；
- 客户邀请链接创建；
- 方案发布前的格式整理；
- 客户反馈录入；
- 成交、丢单和履约结果录入。

### 5.3 六周内禁止扩张

- 语音识别、OCR 和复杂文件解析；
- 新建独立 V6 代码仓库；
- 重写完整客户前端或销售工作台；
- 多 Agent、策略 Agent 和复杂 Agent 协商；
- Temporal 或新的工作流基础设施；
- 完整 CRM、SCRM、合同、支付和财务；
- 完整履约、排期和项目管理；
- 客户多人评论、投票和组织协作；
- 创始人经营看板；
- 多租户 SaaS；
- 为未来规模提前建设 Milvus、消息总线或微服务；
- 与核心验证无关的 UI 精修和旧页面重构。

## 6. AI、人和软件的行为边界

### 6.1 客户侧 Agent

客户侧 Agent 只能：

- 记录客户主动提供的信息；
- 追问影响 Brief 的关键问题；
- 展示已批准的公开案例、资源简介和预算区间；
- 解释客户版 Brief 和已发布方案；
- 接收反馈并转给销售。

客户侧 Agent 永远不能：

- 访问内部成本、毛利、底价、审批记录和销售备注；
- 调用内部报价、CRM写入、资源确认和方案发布工具；
- 承诺正式价格、演员档期、活动效果和合同条件；
- 根据提示词要求突破权限；
- 展示未经授权的演员资料和客户案例。

### 6.2 销售侧 Agent

销售侧 Agent 可以读取内部授权数据并形成建议，但不能：

- 自动向客户发送消息；
- 自动批准报价或折扣；
- 把历史可用档期表述为当前确认档期；
- 修改价格规则和资源事实；
- 在未审批的情况下发布方案；
- 自动将结果写成正式案例。

### 6.3 人工责任

| 决策 | 最终责任人 |
|:---|:---|
| 客户需求是否理解正确 | 销售 + 客户确认 |
| 方案是否适合客户 | 方案审核者 |
| 资源是否真实可用 | 资源审核者 |
| 成本和报价是否准确 | 价格审核者 |
| 对外承诺是否可兑现 | 最终承诺责任人 |
| 是否发送给客户 | 销售 |

## 7. 数据与权限要求

### 7.1 数据分层

```text
原始证据：客户对话、销售导入内容、文件摘录
→ 业务事实：经核对的 Brief 版本
→ 内部方案：资源、报价、成本、毛利、风险和审批
→ 客户快照：审核后生成的独立公开版本
→ 评估记录：模型、提示词、输入、输出、评分和修改
```

### 7.2 客户发布原则

客户接口不得直接读取内部方案后临时删除字段。正式方案必须从已审批内容生成独立客户快照，快照创建后不可修改；如需调整，应创建新版本。

### 7.3 最小安全要求

- 客户通过项目级、可撤销、可过期的专属链接访问；
- 访问令牌只保存哈希，不在日志中记录明文；
- 每次访问校验机会、版本和权限；
- 客户上传内容默认不进入公共知识库；
- 手机号、微信记录和联系人信息脱敏；
- 客户清楚知道正在与 AI 交互，以及数据的用途；
- 对第三方模型发送的数据遵循最小必要原则；
- 客户可以请求删除其验证数据；
- 对话、文件和接口设置速率和大小限制；
- 提示词注入不能扩大工具和数据权限。

## 8. 验证样本与评估方法

### 8.1 样本池

验证开始前应建立：

| 样本 | 最低要求 | 用途 |
|:---|:---:|:---|
| 历史真实需求 | 30—50条，若不足则全部纳入并说明 | 需求类型和字段定义 |
| 核心评估样本 | 不少于20条 | 需求理解、缺口和方案离线测试 |
| 高风险测试集 | 不少于20条，覆盖价格、档期、资源和承诺 | 安全门禁 |
| 可用案例 | 不少于10个 | 检索与方案依据 |
| 资源记录 | 覆盖所选场景的最小可执行集合 | 资源推荐 |
| 真实在谈机会 | 六周内尽可能连续纳入 | 在线验证 |

训练、调试和最终留出样本必须分开。已用于调试的样本不能继续作为最终质量证明。

### 8.2 成功定义预注册

Week 0 完成原流程基线后，产品负责人、业务审核人和验证记录者共同锁定以下定义；六周中途不得为迁就结果而改变。

| 指标 | 默认定义 |
|:---|:---|
| 关键事实准确率 | 与人工确认 Brief 对比，按关键字段逐项统计 |
| 严重错误 | 错误价格、虚假资源、虚假档期、泄露内部信息或产生不可兑现承诺 |
| 可发送方案 | 可直接发送，或只需不改变核心结构、资源组合和价格逻辑的小修改 |
| 有限修改 | 人工修改时间和修改模块比例均低于预注册阈值 |
| 真实使用 | 使用者在真实机会中完成任务，不由创始人代操作 |
| 客户推进 | 客户形成明确回复和下一步商业动作 |
| 持续使用 | 使用者在下一次合适机会中主动继续使用 |

### 8.3 六周核心指标

#### 安全与可信度门槛

- 高风险测试集中严重错误为 0；
- 真实发送方案中资源、价格和档期严重错误为 0；
- 客户版内部信息泄露为 0；
- 每项关键事实、资源和价格均可追溯来源；
- 任一安全门槛未通过，不允许扩大客户使用。

#### 产品价值目标

- 至少 5 个真实客户直接使用需求对话；
- 至少 3 个客户确认 Brief；
- 至少 5 份 Agent 辅助方案真实发送；
- 方案可发送率目标为 80%，样本量过小时同时报告分子和分母；
- 需求整理时间和首版方案时间的中位数较历史基线下降；默认目标为下降 50%，最终阈值在基线后锁定；
- 客户“被理解程度”平均评分目标不低于 4/5；
- 至少 1 名非创始人连续四周在真实机会中使用。

#### 商业链路目标

- 至少 2 个机会进入明确报价、修改、候选或内部审批阶段；
- 目标出现至少 1 个成交或明确丢单；
- 尚未结束的机会继续观察 30—60 天；
- 不以六周成交率作为单独的成败依据。

### 8.4 对照方式

同时记录路径 A 与路径 B：

| 对比维度 | 销售代录 | 客户自助 |
|:---|:---:|:---:|
| 完成率 | 待采集 | 待采集 |
| Brief关键事实准确率 | 待采集 | 待采集 |
| 总沟通轮次 | 待采集 | 待采集 |
| 销售投入时间 | 待采集 | 待采集 |
| 客户确认率 | 待采集 | 待采集 |
| 进入方案比例 | 待采集 | 待采集 |
| 客户推进比例 | 待采集 | 待采集 |

样本量不足时不做显著性结论，只用于识别更有价值的产品入口。

## 9. 六周执行阶段

| 阶段 | 时间 | 唯一重点 | 必须产出 |
|:---|:---|:---|:---|
| P0 | 开始前 | 基线与预注册 | 原流程基线、ICP、样本池、审核人、成功定义 |
| V1 | 第1周 | 数据可信 | 案例、资源、价格规则、测试集和权限清单 |
| V2 | 第2周 | Brief闭环 | 两种输入路径、事实/推断/缺口、版本和确认 |
| V3 | 第3周 | 方案闭环 | 两套方案、结构化检索、确定性预算和风险门禁 |
| V4 | 第4周 | 内部真实使用 | 非创始人使用、记录修改、修复严重问题 |
| V5 | 第5周 | 客户真实使用 | 真实客户对话、Brief确认、方案发送和反馈 |
| V6 | 第6周 | 重复与决策 | 第二轮使用、证据汇总、继续/调整/停止决定 |

每周开发时间只能用于阻塞当前证据获取的问题。不得因为某个未来功能“以后一定需要”而提前开发。

## 10. 六周关卡

### 10.1 继续加码

同时满足以下大部分证据，并通过全部安全门槛：

- Brief 质量稳定，关键事实可追溯；
- 真实方案可发送，人工修改显著下降；
- 至少一条输入路径被真实用户持续采用；
- 产品推动客户进入明确下一步；
- 资源和价格可持续维护；
- 非创始人能够独立使用；
- 价值来自需求理解、方案推演和经营决策，而不只是文案生成。

通过后才进入 V6 产品化阶段，重点建设稳定性、客户体验、标准交付和更多真实机会。

### 10.2 调整后复验

需求理解或方案能力有价值，但出现以下问题：

- 客户不愿直接使用，但销售代录价值明确；
- 需求理解有效，但资源或价格数据不可信；
- 方案质量可用，但双端前端过重；
- 某些场景有效，其他场景差异过大；
- 销售使用有效，但客户反馈功能价值不明显。

应缩小到价值最强的入口和场景，调整后再进行 2—4 周复验，不自动执行完整路线图。

### 10.3 降低优先级或停止

- 非创始人不愿在真实机会中使用；
- 方案仍需整体重写；
- AI主要替代通用文案，对沟通、方案和商业推进无明显影响；
- 真实资源、价格和案例无法持续维护；
- 严重错误或内部数据泄露无法控制；
- 客户直接使用和销售代录两条路径均没有明显价值；
- 为获得基本效果必须持续依赖创始人大量人工干预。

停止当前产品假设，不等于停止“AI驱动非标服务业产品化”的长期职业方向。

## 11. 验收清单

以下均为待验收要求，未完成前不得标记为通过。

### 11.1 功能验收

- [ ] 销售可以导入真实文字需求并生成可核对 Brief；
- [ ] 客户可以通过专属链接完成文字对话并确认 Brief；
- [ ] 系统区分事实、推断和待确认问题；
- [ ] 关键事实可追溯到原始证据；
- [ ] 系统可检索真实案例和资源；
- [ ] 系统能生成两套有实质差异的方案；
- [ ] 报价和毛利由确定性规则计算；
- [ ] 价格、资源、档期和承诺必须人工审核；
- [ ] 客户只读取独立发布快照；
- [ ] 客户反馈和商业里程碑可记录；
- [ ] AI失败时数据不丢失且可转人工。

### 11.2 质量验收

- [ ] 预注册指标已经锁定；
- [ ] 调试集与留出评估集分离；
- [ ] 高风险测试集严重错误为0；
- [ ] 客户版内部信息泄露为0；
- [ ] 重复操作不产生重复版本或业务记录；
- [ ] 模型、提示词、工具、规则和人工修改均可审计；
- [ ] 客户和销售端权限由服务端强制执行。

### 11.3 业务验收

- [ ] 至少5个真实客户直接使用；
- [ ] 至少3个客户确认Brief；
- [ ] 至少5份方案真实发送；
- [ ] 至少2个机会进入明确商业里程碑；
- [ ] 至少1名非创始人连续四周使用；
- [ ] 原流程与Agent流程的时间、修改量和结果已完成对比；
- [ ] 六周后形成继续、调整或停止决定。

## 12. 主要风险

| 风险 | 早期信号 | 预防与应对 |
|:---|:---|:---|
| 双端范围吞噬验证 | 大量时间用于登录、页面和协作功能 | 使用邀请链接和现有H5；前端只做阻塞验证的页面 |
| 客户不愿直接使用 | 链接发送后依然要求销售代填 | 保留销售代录路径，比较两者价值 |
| 方案看起来好但不可发送 | 审核人需要重写结构、资源或价格 | 把“可发送”作为核心评估，不以文案美观替代 |
| 资源与价格不可信 | 频繁出现过期、无来源和人工反复确认 | 指定数据责任人，显示来源、状态和更新时间 |
| 创始人代替用户使用 | 真实销售不主动打开产品 | 强制记录操作者，创始人使用不计入采用指标 |
| 开发吞噬验证 | 开发任务超过数据、客户和测试任务 | 每项开发必须说明它解锁哪条验证证据 |
| 移动成功标准 | 六周中途修改“可发送”和成功阈值 | Week 0预注册并冻结，变更必须保留前后版本 |
| 客户数据或内部信息泄露 | 客户接口能访问内部对象或提示词越权 | 独立客户快照、服务端工具白名单、安全测试 |
| 样本偏差 | 只选择最完整或最熟悉的成功案例 | 纳入缺失、冲突、丢单和高风险样本 |
| 销售周期超过六周 | 机会尚未成交或丢单 | 用商业里程碑做硬指标，延迟观察30—60天 |

## 13. 验证通过后的能力路线

验证通过不等于立即建设完整平台。按以下顺序加码：

1. 稳定最有价值的输入路径和场景；
2. 增加真实机会并提高方案可发送率；
3. 完善资源、价格和评估数据责任；
4. 降低人工交付和创始人依赖；
5. 验证外部机构复制；
6. 再决定是否建设完整双端协作、客户成功和订阅体系。

只有出现明确证据时才拆分子 Agent：

- 单一 Prompt 在方案创造与风险审查之间持续冲突；
- 独立评估显示拆分能显著提高质量；
- 调试、延迟和成本仍在可控范围；
- 业务量足以证明维护额外 Agent 的价值。

## 15. V6.0 → V6.1 关键变化

| V6.0 | V6.1 |
|:---|:---|
| 双端平台作为产品结论 | 双端协作作为优先验证假设 |
| 六周目标与20周开发并存 | 六周验证独立，后续建设全部证据触发 |
| P0主Agent拥有11个工具 | 客户与销售使用不同服务端权限和工具白名单 |
| 内部对象运行时过滤后给客户 | 已审批内容生成独立客户快照 |
| 语音、文档解析、完整工作流并行建设 | 文字输入优先，允许人工后台和Wizard of Oz |
| 11状态覆盖完整经营周期 | 六周只覆盖需求、方案、发布、反馈和商业里程碑 |
| 默认新建V6仓库 | 复用现有仓库和现有可用资产 |
| 方案生成、CRM、履约同时推进 | 核心方案做深，销售流程连接，履约结果回流 |
| 验收项预先标记完成 | 所有验收项保持待验收状态 |
