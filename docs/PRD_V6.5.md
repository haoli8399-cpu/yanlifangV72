## 1. 执行摘要

### 1.1 为什么升级双端

V5.0 把 Agent 定义为"销售的副驾驶"，客户不能直接使用。但实际情况是：

- 客户已经在用通用 AI（DeepSeek/Kimi/豆包）聊活动需求——用的不是我们的数据
- 客户问 DeepSeek "80 人上海团建多少钱"，得到一个泛泛的答案，带着错误预期来找销售
- 销售把客户的话粘贴给 Agent，再手动复制回复发给客户——Agent 的价值被"复制粘贴"给阉割了

**V6.5 的核心判断**：让客户直接用 Agent 描述需求，比让销售做中间人有更好的体验和更高的效率。客户用我们家的 Agent 聊需求——他看到的演员是后仰喜剧真实可用的演员，他拿到的报价是基于真实规则的报价，他确认的 Brief 直接进入 CRM 而不需要销售手打。**这是用 AI 把"客户瞎猜"和"销售手打"两道工序合并了。**

V6.0 不是"给 V5.0 加个客户端"，而是把 V5.0 的单端 Agent 重构为**双端协作系统**——客户端负责表达、确认、反馈，销售端负责判断、推进、成交。两端共享同一份 Brief、方案和项目状态，但看到的权限不同。

### 1.2 V6.0 的核心闭环

```
客户端：客户描述需求 → AI 动态追问 → 确认 Brief → 查看方案 → 反馈
                        ↕ 同一份 Brief、方案、项目状态
销售端：接收需求 → 补全信息 → 生成方案 → 审核发布 → 推进成交 → 履约交接
                        ↕ 多 Agent 协作（主Agent + 方案Agent + 风险Agent）
数据层：案例库 ← 资源库 ← 规则引擎 ← 评估体系
```

### 1.3 MVP 范围

| 模块 | MVP | 后续 |
|:---|:---:|:---:|
| 客户端 AI 需求对话 | ✅ | — |
| 客户端 Brief 确认 | ✅ | — |
| 客户端方案查看 + 反馈 | ✅ | — |
| 客户端多人协作（评论/投票） | ❌ | P1 |
| 销售端工作台（V5.0 已有） | ✅ | — |
| 主 Agent（需求理解 + 工具调用） | ✅ | — |
| 方案 Agent + 风险 Agent（认知隔离） | ❌ | P1 |
| 策略 Agent（商务节奏判断） | ❌ | P1 晚期 |
| 预算/规则引擎 | ✅ | — |
| 案例/资源检索 (pgvector) | ✅ | — |
| 履约交接 + 结果回流 | ✅ | — |

### 1.4 最大变化

| V5.0 | V6.0 |
|:---|:---|
| Agent 只给销售用 | 客户和销售都用，权限不同 |
| 单 Agent + 工具 | 主 Agent（P0）→ 多 Agent 分阶段（P1） |
| 客户需求靠销售手动导入 | 客户直接跟 AI 聊，自动进入 CRM |
| 审批责任模糊 | 审批 UI 显式标注"Agent 生成 vs 你确认" |
| 冷启动是空白工作台 | 三步引导流程（粘贴需求→Agent 分析→一起做方案） |

### 1.5 主要风险

| 风险 | 等级 | 对策 |
|:---|:---:|:---|
| 客户端 Agent 回复质量影响品牌 | 🔴 | 客户版 Agent 评估门槛更高（事实准确率 ≥99%），只展示 public_profile |
| 多人协作复杂度超出 MVP | 🟠 | MVP 仅支持发起人+只读查看，评论/投票推 P1 |
| 双端权限隔离不够导致数据泄露 | 🟠 | 内部成本/毛利/底价字段物理隔离，客户版查询不走同一张表 |
| 冷启动数据准备不足 | 🟡 | 缩小首期 ICP 范围，10 个样本即可启动 |

### 1.6 六周验证重点

- 至少 5 个真实客户直接使用 AI 需求对话
- 至少 3 个客户确认 Brief
- 销售端方案生成可发送率达到 80%
- 至少 2 个机会进入报价或成交阶段
- 客户"被理解程度"评价 ≥ 4/5

## 2. V5.0→V6.0 升级背景

### 2.1 V5.0 的价值和局限

V5.0 建立了正确的方向——AI 经营 Agent 而非 SaaS 平台。但它的设计假设有一个缺口：

**假设销售是需求和方案之间的唯一翻译官。** 这个假设在 B2B 复杂销售场景通常成立，但在企业活动行业存在反例——客户愿意且经常自己描述需求（对 DeepSeek、对 Kimi、对豆包），只是目前没有行业专有的 AI 可用。

### 2.2 从 Codex V6.0 提示词继承的关键决策

| 决策 | V5.0 状态 | V6.0 采纳 |
|:---|:---|:---|
| 双端共用同一份业务事实 | ❌ 不存在客户端 | ✅ 采纳 |
| 客户端负责表达和决策协作 | ❌ 不存在客户端 | ✅ 采纳 |
| 销售端负责经营判断 | ✅ 已有 | ✅ 保留并升级 |
| 客户不能看底价/毛利/内部备注 | ❌ 不适用 | ✅ 采纳 |
| AI 不能直接承诺价格/档期/合同 | ✅ 已有 | ✅ 保留 |
| 多人协作推 P1 | — | ✅ 采纳 |
| 六周验证覆盖客户侧使用者 | ❌ 不覆盖 | ✅ 采纳 |

### 2.3 从多 Agent 架构分析继承的关键决策

在 V5.0 架构设计阶段，我分析了单 Agent vs 多 Agent 的选择。核心结论：

> P0 用单 Agent + 工具是正确的，但架构必须为多 Agent 做好准备。当两个能力需要的模型行为在同一个 prompt 里无法同时被优化时，就应该拆分。

V6.0 采纳分阶段 Agent 策略（2026-07-14 更新）：

| 阶段 | Agent 数量 | 说明 |
|:---|:---:|:---|
| P0 | 1 主 Agent + 11 工具 | 快速验证闭环 |
| P1 第一阶段 | + 3 个专业 Agent | 按业务角色拆分：需求分析师、创意策划师、风控审核师 |
| P1 第二阶段 | + 2 个 → 共 5 个 | 追加资源调度师、报价精算师 |
| P1 晚期 | + 1 个 → 共 6 个 | 追加商务推进师 |
| 长期 | ≤ 6 Agent | 按认知冲突和专业角色拆分，不是按功能模块拆分 |

各 Agent 职责详见 §7.2。

## 3. 产品战略定位

### 3.1 一句话定义

演立方 V6.0 是连接企业客户与商演服务团队的双端 AI 经营协作平台——客户更容易说清需求、理解方案和参与决策，销售更快形成可信方案、完成经营判断并推动成交。

### 3.2 产品不是

- ❌ 客户问卷填写工具
- ❌ PPT/文案自动生成器
- ❌ 通用 CRM 或 SCRM
- ❌ 无人值守的全自动成交平台
- ❌ 活动服务商城或交易撮合平台
- ❌ 完整项目协同软件（不替代 Notion/飞书）

### 3.3 产品是

- ✅ 以需求理解和方案决策为核心的 AI 协作系统
- ✅ 客户和销售围绕同一份业务事实工作的双端平台
- ✅ AI 负责复杂判断、软件负责确定性执行、人负责最终责任
- ✅ 从首次接触到成交复盘的完整经营闭环
- ✅ 第一次验证不是通过"演示效果"，而是真实订单和毛利

## 4. 用户与角色

### 4.1 客户端用户

| 角色 | 描述 | 典型行为 | MVP 支持 |
|:---|:---|:---|:---:|
| **需求发起人** | 行政/HR/市场/品牌/工会/管理者 | 描述需求、补充信息、确认 Brief、查看方案、提交反馈 | ✅ |
| **协作查看者** | 被邀请的同事/领导 | 只读查看方案、查看 Brief | ✅ |
| **决策人** | 有预算审批权的管理者 | 确认最终方案方向、发起报价请求 | ✅ |
| **协作评论者** | 可参与讨论的同事 | 评论、投票、统一反馈 | ❌ P1 |

### 4.2 销售端用户

| 角色 | 描述 | 典型行为 | MVP 支持 |
|:---|:---|:---|:---:|
| **销售** | 直接对接客户的商务人员 | 接收需求、查看 Brief、发起方案、跟进客户 | ✅ |
| **方案策划** | 负责方案内容的专业人员 | 修改方案、审核资源组合、调整内容 | ✅ |
| **资源统筹** | 演员/节目/场馆的调配者 | 确认档期、更新资源状态 | ✅ |
| **报价审核人** | 有价格审批权限的管理者 | 审核报价、确认折扣 | ✅ |
| **项目负责人** | 成交后的履约对接人 | 查看交接包、记录履约结果 | ✅ |
| **管理者** | 创始人/经营者 | 查看指标看板、审核重大决策 | ✅ |

## 5. 产品价值主张

### 5.1 对客户的价值

| 痛点 | V6.0 解决方案 |
|:---|:---|
| 不知道活动怎么办、找谁、花多少钱 | AI 需求顾问帮你梳理，看到真实案例和预算区间 |
| 跟多个供应商重复说一样的话 | 一次说清，Brief 自动同步给销售，不用再说第二遍 |
| 方案看不懂、不知道怎么选 | 多方案对比、差异说明、预算拆解——用你的语言解释 |
| 汇报给领导时说不清楚 | Brief 和方案页直接发给领导看，不用你做 PPT |
| 担心供应商不靠谱 | 看到的是真实演员、真实案例、真实预算，没有"差不多" |

### 5.2 对销售的价值

| 痛点 | V6.0 解决方案 |
|:---|:---|
| 客户需求散落在微信、语音、文件里 | 客户自己跟 AI 聊，结构化需求自动进入工作台 |
| 写方案慢、依赖个人经验 | Agent 生成多套方案草稿，基于真实案例和资源 |
| 不知道下一步该做什么 | Agent 推荐下一最佳行动，标注依据和风险 |
| 成交后信息交接丢三落四 | 自动生成履约交接包，承诺/风险/联系人一目了然 |
| 经验无法沉淀 | 成交/丢单/履约结果自动回流案例库和评估集 |

## 6. 核心业务闭环

### 6.1 端到端闭环

```
┌──────────────────────────────────────────────────────────┐
│                        客户端                             │
│                                                          │
│  微信链接进入 → AI 需求对话 → Brief 确认                  │
│  → 查看方案 → 反馈 → 邀请领导查看                        │
│                                                          │
└──────────────────────────┬───────────────────────────────┘
                           │ 同一份 Brief / 方案 / 项目
┌──────────────────────────┴───────────────────────────────┐
│                       销售端                              │
│                                                          │
│  接收需求 → 补全信息 → 检索案例/资源                      │
│  → 多方案生成 → 预算/风险计算 → 人工审核                  │
│  → 方案发布 → 跟进推进 → 成交/丢单                       │
│  → 履约交接 → 结果回流                                   │
│                                                          │
└──────────────────────────────────────────────────────────┘
                           │
┌──────────────────────────┴───────────────────────────────┐
│                      知识层                               │
│  案例库 ← 资源库 ← 规则引擎 ← 评估体系                   │
└──────────────────────────────────────────────────────────┘
```

### 6.2 机会状态机（11 个状态）

| 状态 | 进入条件 | 客户端可见操作 | 销售端 Agent 动作 |
|:---|:---|:---|:---|
| 新需求 | 客户已输入原始信息 | 继续对话 | 提取事实、识别缺口 |
| 澄清中 | Brief 未达最低完整度 | 回答追问、补充信息 | 动态提问、识别冲突 |
| Brief 就绪 | 核心字段齐全 | 确认 Brief 或提出修改 | 锁定版本、检索案例与资源 |
| 方案生成中 | Brief 已确认 | 等待 | 生成多方案、预算模拟、风险检查 |
| 内部审核 | 方案草稿完成 | 等待 | 运行事实/价格/风险检查 |
| 已发方案 | 客户获得方案链接 | **查看方案、模块反馈、邀请同事** | 追踪行为、生成跟进建议 |
| 商务推进 | 客户提出修改或反馈 | 补充意见、确认方向 | 分析异议、修订方案、建议下一行动 |
| 已成交 | 合同/定金成立 | 查看成交摘要 | 生成履约交接包 |
| 履约中 | 项目已交接 | 查看进度（如有接口） | 汇总承诺、提示风险 |
| 已复盘 | 履约与财务结果可用 | — | 对比方案与实际、提取经验 |
| 已丢单 | 客户拒绝或机会关闭 | — | 归因、识别可复用异议 |

### ② 需求沟通

| # | 功能 | 阶段 | 说明 |
|:---|:---|:---:|:---|
| F01 | 销售粘贴微信文字/语音 → AI 转结构化需求单 | MVP | 自动提取关键字段（活动类型、人数、预算、城市、日期） |
| F02 | AI 识别信息缺口 → 提醒销售追问关键问题 | MVP | 区分"阻塞方案"和"影响可选"两类缺口 |

### ③ 方案策划

| # | 功能 | 阶段 | 说明 |
|:---|:---|:---:|:---|
| F04 | AI 一键生成完整方案 | MVP | 包含：厂牌介绍、节目内容、演员组合（含个人介绍）、档期建议、过往案例 |
| F05 | 方案内嵌自动报价 | MVP | 调用报价规则引擎，报价可追溯规则版本 |
| F06 | 方案自动排版，可直接发给客户 | MVP | 客户版不包含内部成本、毛利、底价 |
| F07 | 销售审核后可手动修改任意部分 | MVP | AI 生成内容与人工修改明确区分 |
| F08 | 审核通过后一键转发给客户 | MVP | 生成专属链接 + 客户版快照 |
| F09 | 客户方案 H5 展示页面 | MVP | 客户侧品牌体验：方案概要、演员简介、案例、报价区间、联系方式 |
| F10 | 方案快照机制 | MVP | 生成时冻结引用数据（演员信息、报价规则版本、案例），后续修改不影响已发方案 |
| F11 | 客户查看方案行为追踪 | P1 | 销售知道客户是否打开、查看时长、关注模块 |
| F12 | 方案版本对比 | P1 | 客户可对比 V1/V2 差异，一眼看出改了什么 |

### ④ 报价规则引擎

| # | 功能 | 阶段 | 说明 |
|:---|:---|:---:|:---|
| F13 | 后台维护报价规则（底价、分成比例、折扣边界、毛利底线） | MVP | 运营/财务维护，销售不可见底价 |
| F14 | 规则版本化 + 更新日志 | MVP | 每次修改生成新版本号，历史规则可追溯 |

### ⑤ 合同

## 7. 多 Agent 架构设计

### 7.1 架构原则

1. **P0 用 1 个 Agent，但架构设计成 N 个可插拔。** 工具和子 Agent 使用相同的调用接口——从主 Agent 视角看，`风险检查工具` 和 `风险审查 Agent` 是同一个抽象。
2. **按认知冲突拆分，不按功能模块拆分。** 方案生成（创造性、乐观）和风险检查（保守、怀疑）天然冲突——一个人不能既推销方案又审计方案。
3. **每个 Agent 有独立的 prompt、工具白名单、评估集。** 不能让风险 Agent 有权限修改方案内容，不能让方案 Agent 有权限修改价格规则。
4. **总数不超过 6 个。** 按业务专业角色拆分，每个 Agent 对应一个真实经营岗位的认知职责。

### 7.2 分阶段 Agent 部署

#### P0（第 3-12 周）：主 Agent

```
┌─────────────────────────────────────────┐
│              主 Agent                    │
│  (LangGraph StateGraph)                  │
│                                          │
│  职责：                                  │
│  • 需求理解与缺口识别                    │
│  • 动态追问策略                          │
│  • 调用 11 个工具                         │
│  • 结构化输出                             │
│  • 下一行动建议                           │
│                                          │
│  工具白名单（11 个全部可用）：            │
│  InputParser, BriefTool, CaseSearch,     │
│  ResourceSearch, BudgetEngine,           │
│  PlanGenerator, RiskChecker,             │
│  ProposalPublisher, CRMTool,             │
│  ActionAdvisor, OutcomeRecorder          │
└─────────────────────────────────────────┘
```

**为什么 P0 只有一个 Agent？** 调试快（一条链路）、迭代快（改一个 prompt）、失败面小（只有一种错误模式）。

#### P1 第一阶段（第 13-16 周）：上线 3 个专业 Agent

从 P0 的单 Agent 拆出三个解决认知冲突的专业角色：

```
┌──────────────────────────────────────────────────────────────┐
│                     主 Agent (协调者)                         │
│  职责：任务规划、工具路由、上下文管理、审批衔接               │
│                                                              │
│  ┌──────────────────┐ ┌──────────────────┐ ┌──────────────┐ │
│  │  需求分析师       │ │  创意策划师       │ │ 风控审核师    │ │
│  │  Analyst          │ │  Planner          │ │ Auditor       │ │
│  │                  │ │                  │ │              │ │
│  │ 人格：结构化、   │ │ 人格：创造性、   │ │ 人格：保守、  │ │
│  │ 精确、不遗漏     │ │ 有观点、敢推荐   │ │ 怀疑、零容错  │ │
│  │                  │ │                  │ │              │ │
│  │ 职责：           │ │ 职责：           │ │ 职责：        │ │
│  │ 理解模糊需求     │ │ 基于Brief生成    │ │ 检查方案中的  │ │
│  │ →提取事实       │ │ 两套实质差异方案 │ │ 风险承诺、资源│ │
│  │ →识别缺口       │ │ 解释取舍和优势   │ │ 冲突、毛利偏差│ │
│  │ →追问关键问题   │ │                  │ │ 违规表述      │ │
│  │ →形成Brief      │ │ 工具：           │ │              │ │
│  │                  │ │ CaseSearch       │ │ 工具：        │ │
│  │ 工具：           │ │ ResourceSearch   │ │ BudgetEngine  │ │
│  │ InputParser      │ │ PlanGenerator    │ │ RiskChecker   │ │
│  │ BriefTool        │ │                  │ │              │ │
│  └──────────────────┘ └──────────────────┘ └──────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

**为什么拆这三个？** 需求分析（精确、结构化）和创意策划（发散、有观点）和风险审核（保守、挑刺）是三种完全不同的认知模式。一个人不能既保证不遗漏事实，又大胆推荐方案，再同时审计自己的推荐。

#### P1 第二阶段（第 17-20 周）：追加 2 个 → 共 5 个

三个核心 Agent 稳定后，追加两个补充角色：

| 新增 Agent | 对应岗位 | 职责 | 认知特征 |
|:---|:---|:---|:---|
| **资源调度师** ResourceCoordinator | 运营/资源经理 | 检索演员、节目、场地、档期，标注可用状态和风险 | 精确、标注来源、不说"可能" |
| **报价精算师** PricingActuary | 财务/定价 | 基于规则计算成本和报价，守住毛利底线 | 精确、零容错、保守 |

拆出理由：资源匹配从创意策划师中拆出——策划师负责"用什么资源最合适"，调度师负责"这些资源现在能不能用"；报价从风控审核师中拆出——精算师算价格，审核师审风险，职责分离。

#### P1 晚期（第 21-24 周）：追加商务推进师 → 共 6 个

```
主 Agent → 需求分析师 + 创意策划师 + 风控审核师 + 资源调度师 + 报价精算师 + 商务推进师

商务推进师 DealAdvancer：
  职责：商务推进节奏判断
  输入：当前机会状态 + 客户反馈 + 历史互动
  输出：下一最佳行动（含时机、话术建议、需要确认的事项）
  人格：懂销售节奏、知道什么时机说什么话、知道什么时候该催什么时候该等
```

**为什么单独拆？** 商务推进需要"节奏感"和"分寸感"——和需求分析、方案生成、风险审查是完全不同的认知能力。

#### 长期（第 24 周后）：不再增加 Agent

6 个 Agent 是上限——每个对应真实商演经营中的一个专业岗位。如果未来发现需要第 7 个，先问自己：这是认知冲突，还是功能模块？如果是后者，加工具，不是加 Agent。

### 7.3 Agent 调用接口（统一抽象）

所有 Agent 和工具使用相同的调用接口：

```python
# 工具接口
class ToolResult:
    tool_name: str
    output: dict
    source: str                # 数据来源
    updated_at: datetime       # 数据更新时间
    confidence: Literal["confirmed", "pending", "estimated"]

# Agent 接口（与工具接口兼容）
class AgentResult(ToolResult):
    agent_name: str            # "plan_agent" / "risk_agent" / "strategy_agent"
    reasoning: str             # Agent 的推理过程
    tool_calls: list[dict]     # Agent 调用了哪些工具
    evaluation_passed: bool    # 是否通过本 Agent 的评估标准

# 主 Agent 调用子 Agent 和工具的方式完全相同
main_agent.run([
    call_tool("CaseSearch", query=...),
    call_agent("plan_agent", brief=..., resources=...),
    call_agent("risk_agent", plan=..., budget=...),
])
```

**关键设计**：主 Agent 调用子 Agent 和调用工具的代码完全一样。P0 先把 `RiskChecker` 做成规则工具（确定性），P1 发现规则覆盖不够时，把 `RiskChecker` 替换成 `RiskAgent`（LLM 判断），主 Agent 一行不改。

## 8. 端到端用户旅程

### 流程 A：客户主动进入

```
客户通过微信链接/官网/销售分享进入
→ 看到场景选择（企业团建/年会/发布会/客户答谢/其他）
  [选择"企业团建"]
→ AI 需求顾问对话界面
  AI："你好！你想为企业策划什么样的团建？比如人数、时间、预算、想要的氛围？"
  客户："80 人，8 月中旬，上海，预算 10 万左右，主要是想加强跨部门协作"
→ AI 识别：
  ✅ 事实：团建、80 人、8 月中旬、上海、约 10 万、加强跨部门协作
  ❓ 缺口：活动时长？户外还是室内？有没有特别不想做的？谁拍板？
  AI："大概多长时间？一天还是两天一夜？"
  客户："两天一夜吧"
  AI："了解。有没有特别忌讳的——比如高空项目、极端体力活动？"
  客户："领导说了，安全第一，不要太极限"
→ Brief 生成：展示已确认信息 + AI 推断 + 待确认事项
  客户确认 Brief
→ AI："好的，你的需求我已经整理好了。后仰喜剧的顾问会根据你的需求匹配方案，预计 24 小时内发给你。留个联系方式？"
  客户填写手机号 → 自动创建销售机会
```

**验收重点**：客户独立完成，无需销售介入；对话轮次不超过 6 轮；客户觉得"被理解了"。

### 流程 B：销售代客户导入

```
销售收到客户微信
→ 登录销售端工作台 → 新建机会
→ 粘贴客户聊天记录或上传文件
→ Agent 提取需求 → 生成待确认 Brief
→ 销售选择"发给客户确认"
→ 客户收到轻量链接，补充或确认 Brief
→ Brief 回到销售端，标注"客户已确认部分"vs"销售需补充部分"
```

### 流程 C：方案生成与审核

```
Brief 确认
→ Agent 检索相似案例（Milvus/pgvector）
→ Agent 检索候选资源（演员、主持、节目、场馆）
→ Agent 生成 2-3 套方案（保守/平衡/突破）
→ 预算引擎计算成本/报价/毛利
→ 风险检查器识别档期/场地/预算/承诺风险
→ 人工审核（方案负责人→商务负责人→资源负责人）
→ 审批通过 → 生成客户版方案 H5
```

### 流程 D：客户查看与反馈

```
客户收到方案链接
→ 方案总览页：核心亮点 + 活动流程 + 预算区间
→ 方案对比（如有 2-3 套）：列表对比
→ 对模块反馈：👍 喜欢 / 👎 不太合适 / 💬 需要调整
→ 填写反馈："领导觉得脱口秀时间太长，能不能减到 20 分钟，多加点乐队互动？"
→ 销售端收到反馈摘要 + AI 修订建议
```

### 流程 E：销售推进

```
收到客户反馈
→ Agent 总结："客户关注点：① 脱口秀时长；② 乐队互动；③ 未提预算问题 = 价格可接受"
→ Agent 建议修改：
  "建议将呼兰脱口秀从 40 分钟调整为 20 分钟，新增房东的猫乐队互动 30 分钟，预算变化约 +¥3,000"
→ 销售修改方案 → 生成 v2 版本
→ 客户确认 v2 → 进入报价/成交
```

### 流程 F：成交与履约回流

```
成交
→ Agent 自动生成履约交接包：
  - 最终 Brief + 最终方案 + 最终报价
  - 已确认资源清单（呼兰 8/16 14:00-15:00，档期已锁定）
  - 客户承诺清单
  - 风险清单 + 待确认事项
  - 客户关键联系人
→ 项目结束 → 录入实际收入/成本/毛利/异常/满意度
→ 经审核的案例 → 入库为可检索案例
→ 失败样本 → 进入评估集
```

## 11. AI Agent 能力设计

### 11.1 主 Agent（P0 唯一 Agent）

**职责**：需求理解、工具调用、方案生成、风险检查、行动建议

**核心能力模块**：

| 能力 | 输入 | 输出 | Agent/工具 |
|:---|:---|:---|:---|
| 客户需求理解 | 非结构化文字/语音 | facts/inferences/gaps | Agent 推理 |
| 销售需求分析 | 客户原始输入 + 历史互动 | 结构化需求 + 角色识别 + 风险预警 | Agent 推理 |
| 动态追问 | 当前 gaps | 不超过 5 个关键问题 | Agent 推理 |
| 方案推演 | Brief + 案例 + 资源 | 2-3 套差异化方案 | Agent 推理 + PlanGenerator |
| 资源匹配 | 活动目标/预算/城市/档期/风格 | 候选资源 + 匹配理由 + 可用状态 | ResourceSearch (pgvector) |
| 预算计算 | 资源组合 + 规则 | 成本/报价/毛利 + 异常标记 | **BudgetEngine（规则引擎，不用 LLM）** |
| 风险检查 | Brief + 方案 + 价格 + 资源 | 风险等级（R0-R3）+ 原因 + 处理要求 | RiskChecker（规则 + LLM 双重） |
| 行动建议 | 机会状态 + 历史互动 | 下一行动 + 建议时间 + 依据 | Agent 推理 |
| 反馈总结 | 客户反馈文本 | 异议归纳 + 修订建议 + 影响分析 | Agent 推理 |
| 结果学习 | 成交/丢单/履约数据 | 案例候选项 + 评估样本 + 规则建议 | Agent 推理 + 人工审核 |

### 11.2 Agent 行为约束（客户端 vs 销售端）

| 操作 | 客户端 | 销售端 |
|:---|:---|:---|
| 展示演员资料 | ✅ 仅 public_profile（姓名/照片/风格/案例标题/价格区间） | ✅ 全部信息含底价 |
| 展示预算区间 | ✅ 区间（"约 ¥8-12 万"） | ✅ 精确数字 + 成本 + 毛利 |
| 确认档期 | ❌ 标注"需确认" | ⚠️ 标注来源和可用状态 |
| 生成正式报价 | ❌ | ⚠️ 需人工审批 |
| 发送外部消息 | ❌ | ❌ 永远不能（需人工手动发送） |
| 编造资源 | ❌ | ❌ |
| 承诺成交/效果 | ❌ | ❌ |

```sql

ALTER TABLE users ADD COLUMN public_name TEXT; -- 对外展示名

-- 2. 原始证据表（不可变）
CREATE TABLE evidences (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    recorded_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ DEFAULT now()
);

-- 3. Brief 版本表（版本化）
CREATE TABLE brief_versions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    version INTEGER NOT NULL,
    facts JSONB,                 -- [{field, value, confidence, evidence_ids, source_quote}]
    inferences JSONB,            -- [{field, value, confidence, basis}]
    open_questions JSONB,        -- [{question, field, impact, status}]
    constraints JSONB,           -- {hard_constraints: [...], soft_preferences: [...]}
    completeness_score INTEGER,  -- 0-100
    status TEXT DEFAULT 'draft', -- 'draft' | 'pending_customer' | 'customer_confirmed' | 'deprecated'
    confirmed_by TEXT,           -- user_id（客户或销售）

);

-- 4. 方案版本表（版本化，双价格字段）
CREATE TABLE plan_versions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    opportunity_id UUID REFERENCES opportunities(id),
    schema_version TEXT NOT NULL DEFAULT '1.0',
    version INTEGER NOT NULL,
    strategy TEXT,               -- 'conservative' | 'balanced' | 'breakthrough'
    structure JSONB,
    resources JSONB,             -- [{resource_id, type, quantity, customer_price, internal_cost}]
    budget JSONB,                -- {total_customer_price, total_internal_cost, margin, breakdown}
    risks JSONB,
    advantages TEXT[],
    tradeoffs TEXT[],
    status TEXT DEFAULT 'draft', -- 'draft' | 'internal_review' | 'approved' | 'published' | 'deprecated'

);

-- 5. 客户反馈表
CREATE TABLE customer_feedback (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    opportunity_id UUID REFERENCES opportunities(id),
    plan_version_id UUID REFERENCES plan_versions(id),
    feedback_type TEXT,          -- 'like' | 'dislike' | 'adjust' | 'comment'
    module_target TEXT,          -- 针对哪个模块
    content TEXT,
    submitted_by UUID REFERENCES users(id),
    created_at TIMESTAMPTZ DEFAULT now()
);

-- 6. 审批记录表
CREATE TABLE approvals (

CREATE TABLE actions (

    completed_at TIMESTAMPTZ,

CREATE TABLE outcomes (

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE case_embeddings (
```

## 14. 安全与数据隔离

### 14.1 客户端安全

- 微信链接进入 → 手机号验证 → 一次性 Token → 项目级权限
- 链接可设置有效期（默认 30 天）
- 同一个机会的多个协作者通过邀请链接加入（MVP 不支持，P1 支持）
- 客户无法通过修改 URL 访问其他客户的机会

### 14.2 AI 身份说明（客户端必须展示）

```
┌─────────────────────────────────────────────┐
│ 🤖 你正在与后仰喜剧 AI 活动顾问交流          │
│                                             │
│ AI 会帮你梳理需求，但不能代你：               │
│ • 给出最终报价（需人工确认）                  │
│ • 承诺演员档期（需人工确认）                  │
│ • 签署合同或作出效果承诺                      │
│                                             │
│ 如需人工服务，随时拨打：400-xxx-xxxx          │
└─────────────────────────────────────────────┘
```

### 14.3 内部数据防泄露

- 客户 API 接口不返回 `internal_cost`、`margin`、`approval_log`、`internal_data` 字段
- 数据库查询层：所有客户侧查询默认 `WHERE is_public = true`（案例）、`public_profile IS NOT NULL`（资源）
- Agent 对客户回复前，通过 Schema 校验：禁止出现 ¥（成本）、毛利、底价、其他客户信息
- 日志中客户敏感信息（手机号）脱敏

### 15.3 后续扩展路线：完整经营闭环

当前 MVP 聚焦**销售闭环**（需求→方案→报价→成交），以下环节先通过人工流程管理，在后续阶段系统化：

| 环节 | 当前 MVP | G4（第13-16周） | G5+（第17周后） |
|:---|:---|:---|:---|
| **合同** | 人工签署，不做系统 | 合同模板 + 关键条款对账 | 电子签对接 + 合同版本管理 |
| **支付** | 人工收款、线下记录 | 定金/尾款节点记录 | 支付链接 + 收款状态同步 |
| **履约执行** | 人工对接演员/场地/客户 | 履约交接包自动生成（已有） | 履约任务看板 + 异常预警 + 进度同步 |
| **客户评价** | 人工问、口头记 | 结构化评价表单（NPS + 分项评分） | 评价→案例库自动回流 + 差评预警 |
| **复购触达** | 销售主动跟进 | 客户分级 + 复购机会识别 | AI 复购建议 + 自动化触达 |
| **利润分析** | 手工算 | 项目毛利自动计算 | 按客户/类型/销售等多维度利润看板 |

**设计原则**：
- 每阶段只加「没有它经营数据就失真」的能力，不加「好像应该有」的功能
- 合同/支付优先保证数据准确（金额、节点、归属），不追求电子签和在线支付
- 履约和评价先确保结果回流到案例库，再考虑过程管理
- 所有扩展模块复用同一套数据底座（opportunity、plan_version、quote），不另建数据孤岛

## 技术架构与实施方案

> 以下为 2026-07-14 产品负责人与 Hermes 教练联合确认的完整技术架构。涵盖：整体架构、数据库、API、前端、AI Agent、认证、部署、通知、文件存储、测试、开发计划。

---

### 一、整体架构

**三端应用，共享一个模块化后端。**

```
┌──────────────────────────────────────────────┐
│                  Nginx (80/443)              │
│                                              │
│  /api/*   → Fastify:3000                     │
│  /admin/* → PC 管理端静态文件 (React SPA)      │
│  /c/*     → 客户应用静态文件                   │
│  /a/*     → 演员应用静态文件                   │
└──────────────────────────────────────────────┘
          │
┌─────────┴────────────────────────────────────┐
│              Fastify (模块化单体)              │
│                                              │
│  src/internal/   PC 管理端 API（销售+运营）     │
│  src/customer/   客户应用 API（只读 + 反馈）     │
│  src/actor/      演员应用 API（执行单 + 签到）   │
│  src/shared/     共享层（数据库/认证/存储/配置）  │
└──────────┬───────────────────────────────────┘
           │
    ┌──────┴──────┬──────────┬──────────┐
    │             │          │          │
  PostgreSQL    Redis     MinIO     DeepSeek
  (32 张表)     (缓存+     (文件      (AI 模型)
                限流)      存储)
```

**三端前端**：

| 端 | 用户 | 设备 | 技术栈 |
|:---|:---|:---|:---|
| PC 管理端 | 销售 + 运营 | PC | React 19 + TanStack Router + shadcn/ui + Tailwind CSS |
| 客户应用 | 企业客户 | 手机 + 电脑（响应式） | 同上，品牌展示风格 |
| 演员应用 | 演员 | 手机（H5） | 同上，极简轻量 |

**UI 策略**：不 Fork 任何 Starter。用 shadcn/ui 组件 + 参考 Shadcn Admin 布局模式搭建后台骨架。建立 Design Reference Library：按模块参考 Attio（CRM 信息流）、Cursor（AI Copilot 交互）、Linear（项目状态流转）、Notion（结构化内容展示）、Vercel Analytics（仪表盘）。

**多进程升级路线**：当前 `internal/` `customer/` `actor/` 三个目录互不 import。拆独立服务时只改启动入口，不改业务代码。拆的规则：不共享内存状态、不跨目录 import、独立数据库连接。

### 二、数据库设计

**32 张表，分 11 个模块。**

| 分类 | 表数 | 表名 |
|:---|---:|:---|
| 系统基础 | 5 | users, organizations, contacts, audit_logs, system_configs |
| 机会需求 | 3 | opportunities, evidences, brief_versions |
| 演员资源 | 4 | actors, actor_stats, venues, cases |
| 报价规则 | 2 | price_rules, price_rule_versions |
| 方案 | 3 | plans, plan_versions, plan_snapshots |
| 合同 | 1 | contracts |
| 支付 | 2 | payment_schedules, payment_records |
| 履约 | 3 | execution_sheets, actor_checkins, execution_issues |
| 评价复购 | 2 | evaluations, renewal_flags |
| 客户侧 | 4 | share_tokens, actor_access_tokens, public_snapshots, customer_views |
| AI | 2 | ai_runs, prompt_versions |
| 通知 | 1 | notifications |

**设计原则**：方案快照冻结引用数据、物理隔离内部成本与客户可见字段、全部关键实体版本化、区分客户提供/销售补充/AI推断/人工确认。

**文件存储**：MinIO（S3 兼容），Docker Compose 自部署。所有文件统一通过上传接口 → 数据库只存 URL。public bucket（演员照片、案例图片）和 private bucket（合同 PDF、备份）分离。

---

### 三、API 设计

**一个 Fastify 进程，三组路由前缀。**

```
/api/internal/*    PC 管理端（销售 + 运营）  → JWT + role 中间件
/api/customer/*    客户应用                   → share_token 中间件
/api/actor/*       演员应用                   → actor_access_token 中间件
```

**目录隔离**：`src/internal/` `src/customer/` `src/actor/` 三个目录互不 import。`src/shared/` 提供数据库连接、认证、存储等共享能力。客户 Repo 只查 public 视图/字段（不含 cost, margin），内部 Repo 查全量。

**数据快照**：方案生成时，涉及的外部数据（演员信息、报价规则版本、案例）复制一份冻结在 `plan_snapshots`。后续演员离职、规则变更、案例下架——已发方案不受影响。

### 四、AI Agent 方案

**模型**：deepseek-v4-pro（P0 单一模型），备用 Claude/GPT-4o。

**8 项核心决策**：

| # | 决策 | 方案 |
|:---|:---|:---|
| 1 | 模型策略 | P0 单一模型全包，P1 不同 Agent 可选不同模型 |
| 2 | Prompt 管理 | 版本化文件 + 注册表，`ai_runs` 记录 prompt_version |
| 3 | 结构化输出 | JSON Schema 强约束，失败重试 1 次，**支持部分成功恢复** |
| 4 | 工具调用 | 两步检索（SQL 过滤 → pgvector 排序），LLM 只看到精选候选集 |
| 5 | 失败降级 | 步骤级进度反馈 + 部分成功保存 + 完全失败转人工 |
| 6 | RAG | pgvector + DeepSeek embedding，增量更新，结果标注来源和更新时间 |
| 7 | 质量评估 | 20 条离线评估集（准确性/完整性/安全性/可用性/差异性） + 上线后人工评分趋势 |
| 8 | 成本控制 | ¥30/机会硬上限，`ai_runs` 全量记录每次调用的 token 和费用 |

**Agent 演进**：P0 单 Agent + 6 个工具 → P1 第一阶段 3 个专业 Agent（需求分析师/创意策划师/风控审核师）→ P1 第二阶段 +2 个（资源调度师/报价精算师）→ P1 晚期 +1 个（商务推进师）。

### 五、认证体系

**两种认证方式，三类用户。**

| | 内部用户 | 客户 | 演员 |
|:---|:---|:---|:---|
| 认证方式 | 手机号 + 密码 + JWT | share_token（专属链接） | actor_access_token（专属链接） |
| 有效期 | JWT 7 天 | 每次访问自动重置 30 天 | 演出后 24 小时 |
| 权限范围 | JWT 含 role（sales/operations/finance/admin） | 绑定到单个 opportunity | 绑定到单个 actor + execution_sheet |
| 密码存储 | bcrypt hash | 无 | 无 |
| Token 存储 | — | 只存 SHA256 hash | 只存 SHA256 hash |
| 撤销 | JWT 黑名单即时生效 | 销售随时撤销 | 不支持（不需要） |
| 首次启动 | seed.sql 创建默认 admin，首次登录强制改密码 | — | — |

**安全措施**：登录频率限制（5 次失败/15 min 锁定）、JWT 黑名单（`revoked_tokens` 表，中间件每次请求校验）。

### 六、部署方案

**Docker Compose，单机部署，三环境。**

```
docker-compose.yml
├── postgres:16   (5432，Docker volume 持久化)
├── minio         (9000，Docker volume 持久化)
├── redis:7       (6379，缓存 + 限流)
├── fastify       (3000，API 服务)
└── nginx         (80/443，前端静态文件 + 反向代理 + Let's Encrypt SSL)
```

| 环境 | 用途 | 数据库 | 部署方式 |
|:---|:---|:---|:---|
| dev | 本地开发 | 本地 PostgreSQL | `docker compose up` |
| staging | 上线前验证 | 独立测试数据库 | 同机器不同端口 |
| production | 正式环境 | 生产数据库，每日 pg_dump 备份 | `docker compose up -d` |

**CI/CD**：GitHub Actions → 跑测试 → 构建 Docker 镜像 → 推送到服务器 → `docker compose up -d`。

**监控**：`/api/health` 端点检测 DB/Redis/MinIO/DeepSeek 连通性。AI 失败率超过 30% 告警。

| 单元测试 | 报价规则引擎、风险检查器、Brief 解析器、状态机 | 核心逻辑 100% | 每次 git push |
| 集成测试 | 每个 API 端点（正常 + 异常 case） | 全部 API | 每次 git push |

### 九、开发计划

**5 阶段，12 周。**

| 阶段 | 周次 | 主题 | 功能数 | 里程碑 |
|:---|:---|:---|:---:|:---|
| P0 | 第 1-2 周 | 地基 | 8 项 | 环境 + 认证 + 权限 + 建表 + 数据导入 |
| P1 | 第 3-5 周 | 需求→方案 | 10 项 | 销售能生成方案、客户能看到 |
| P2 | 第 6-7 周 | 成交 | 6 项 | 合同 + 支付闭环 |
| P3 | 第 8-10 周 | 履约→评价 | 8 项 | 执行单 + 评价回流 + 仪表盘 |
| P4 | 第 11-12 周 | 收尾 | 3 项 | 客户详情 + 通知 + 上线 |

**关键依赖**：演员/案例数据 + 报价规则 → 方案生成 → 合同 → 支付 → 执行单 → 评价。

**P1 功能**（第 13-14 周）：客户自助需求、方案追踪、版本对比、异常记录。

**后期功能**（第 15 周+）：电子签、自动案例、转介绍、多维分析、Agent 拆分（3→5→6）、微信通知自动化。
