# 重大决策记录

> **每项重大技术/产品决策必须记录。不记录等于没发生。**

---

## 决策记录格式

```
### {日期} — {决策标题}

- **决策内容：** 做了什么决定
- **背景：** 当时面临什么问题
- **原因：** 为什么选这个方案
- **备选方案：** 还考虑了哪些
- **为什么不选其他方案：** 淘汰理由
- **影响范围：** 涉及哪些模块/文档
- **涉及版本：** 影响的版本号
- **是否可逆：** 能否在未来改回来
- **后续观察项：** 需要关注什么
```

## 决策记录

### 2026-07-10 — 品牌色选定 `#5B4FD6`

- **决策内容：** V4.7 品牌主色定为 `#5B4FD6`（沉稳紫）
- **背景：** 项目从 Lovable 迁移，初始色为 `#6E59F5`，V4.6 为 `#7c3aed`
- **原因：** `#5B4FD6` 比 Lovable 的 `#6E59F5` 深一度，面向企业客户时更沉稳，符合"企业级SaaS"定位
- **备选方案：** `#6E59F5`（Lovable 默认）、`#7c3aed`（V4.6 色）
- **为什么不选其他方案：** `#6E59F5` 在企业场景略显轻浮；`#7c3aed` 已淘汰
- **影响范围：** 全部前端代码、Design System、小程序
- **涉及版本：** V4.7
- **是否可逆：** 理论上可，但成本极高（全量替换）
- **后续观察项：** 代码中 `#6E59F5` 和 `#7c3aed` 残留需持续清理

### 2026-07-10 — 六端设计变量定版

- **决策内容：** 六个端（增长工具H5/客户方案H5/企业PC/移动Web/销售工作台/运营后台）各自的设计变量正式确定
- **背景：** V4.7 从单体应用演变为多端架构，需差异化设计策略
- **原因：** 不同端的用户场景和信息密度天差地别，一刀切体验差
- **影响范围：** `V4.7_Design_System_Final.md`、所有前端代码
- **涉及版本：** V4.7
- **是否可逆：** 设计变量可调整，但六端架构是固定的

### 2026-07-10 — 多 Agent 协作模式确立

- **决策内容：** AI EM 工作流定版：Hermes 分析→出Design System文档→写Agent prompt→delegate_task 并行委派→审查
- **背景：** 项目进入多 Agent 开发阶段，需要明确调度机制
- **原因：** 先文档后代码、最多 3 个 Agent 并行、Hermes 不直接写代码
- **影响范围：** `project-center/`、所有 Agent 工作流
- **涉及版本：** V4.7
- **是否可逆：** Agent 数量和分工可调整

### 2026-07-10 — 代码修改权限收归 Hermes

- **决策内容：** Hermes 及子 Agent 严禁在未经豪哥明确授权的情况下直接生成/修改代码。替代方案：创建任务文件到 `~/Desktop/agent-tasks/`，由外部 Agent 自行读取执行
- **背景：** 防止多 Agent 无边界修改导致代码混乱
- **原因：** 产品方向控制和代码质量管理
- **影响范围：** Hermes 行为、Agent 开发流程
- **涉及版本：** V4.7
- **是否可逆：** 紧急情况下 Hermes 可记录决策后直接执行

### 2026-07-11 — Engineering OS 初始化

- **决策内容：** 在项目根目录建立 `docs/` 工程管理体系，包含五份核心事实源 + 配套文件
- **背景：** 项目从 project-center 的分散文档升级为系统化工程管理体系
- **原因：** 规范 Agent 行为、防止代码漂移、建立版本管理能力
- **影响范围：** 新增 `docs/`、`AGENTS.md`、`project-state.json`
- **涉及版本：** V4.7
- **是否可逆：** 文档体系可调整
- **后续观察项：** 工程阶段从 A 升级到 B 的时机

## 需要记录的内容类型

以下变更必须记录到本文件：

- 技术栈变化（新增/替换/升级核心依赖）
- 数据库结构变化（新增表/修改核心字段）
- 核心产品逻辑变化（功能范围/用户流程）
- UI 基线变化（Design System 大调整）
- Agent 分工变化
- 部署方式变化
- 重大依赖升级（主版本号跨越）
- 删除功能
- 架构重构
- 安全策略变化
